## GROUP 1 — WRITING-METHOD / ARCHITECTURE

### B1. The dependency graph is SIX typed registries, not one — the ledger fused "concept dependencies" into "threads"  · ABSENT · HIGH
- **Source (ARCHITECTURE §4, verbatim):** *"Six dependency types operate across modules. Each is tracked in a specific registry file."* — namely **§4.1 Concept Dependencies** (`registry/dependencies.md`), **§4.2 Thread Dependencies** (`registry/threads.md`), **§4.3 Compression-Pair** (`compression_pairs.md`), **§4.4 Refrain** (`refrain.md`), **§4.5 Canonical-Source** (`canon_dependencies.md`, auto-generated from contracts), **§4.6 Fiction-Substrate** (in each contract). Concept-deps have their OWN rule and format: *"No term may be used in module N before its introduction module N₀ ≤ N"* with a 12-entry `C-01…C-12` map (each: Introduced / Available / Brief-forward-references-allowed).
- **Ledger has:** §2.3 lists the registry set as *"threads, dependencies, compression_pairs, refrain, canon_refs"* and §CLAUDE §6 loads "all registries," and `audit dependencies` exists for "forward references." So the *names* are present — but the ledger nowhere states that **concept-introduction-order is a DISTINCT registry from seeds/payoffs** with its own `C-NN: Introduced/Available/brief-forward-allowed` schema. The two are conceptually merged ("threads/callbacks resolve, no forward concept references" — GATE-3 treats them as one gate). The **"brief forward reference ALLOWED"** carve-out (a preview of a term before its full introduction is legal; a *use* is not) is absent entirely — and that nuance is exactly what keeps `audit dependencies` from false-positiving on the flash-forwards §7 mandates.
- **Bake-in:** `KIT_ARCHITECTURE.md` §(b) per-book workspace + ledger §2.3 — add `registry/dependencies.md` as a FIRST-CLASS concept-order registry distinct from `threads.md`, with the `C-NN: Introduced / Available / Brief-forward-refs-allowed` schema. `audit_dependencies` (already named in the toolchain) must honor the "brief forward reference allowed" exception so it does not fight the flash-forward technique (B7). Note the `canon_dependencies.md` is **auto-generated from the contracts' Canon-Anchors field** — record that generation direction.

### B2. Threads carry an `Immunity: true|false` flag — immune threads are frozen against revision reshaping  · ABSENT · HIGH
- **Source (ARCHITECTURE §4.2 + SEED §4, verbatim):** every thread record ends with `Status:` and **`Immunity:`**. The refrain thread: *"T-15 … Immunity: TRUE (exact wording; 6 placements; not variable)."* By contrast T-01 (Tuesday Afternoon): *"Immunity: false (could be reshaped during revision if register drifts)"*; T-11 (Katherine): *"Immunity: false (could be cut if Bo prefers)."* The flag marks which seeds/motifs a revision pass may reshape and which are **load-bearing-locked**.
- **Ledger has:** ABSENT. §17.1/§2.7 lock the refrain wording+count, and §11 makes markdown append-only — but there is no per-thread *mutability* bit in the registry, so a revise-pass has no machine-readable signal for "this motif is frozen, that one is reshapeable." The refrain is protected by a special-case; every OTHER immune thread (the invariant Disposition, "love as epistemic treason", the compression-pair) has no such marker.
- **Bake-in:** ledger §2.6 (registry discipline) + `templates/threads.template.md` — add an `Immunity: true|false` field to every thread record; wire `audit threads` to refuse a revise-pass edit that reshapes an `Immunity: true` thread's load-bearing content (the refrain is then just one immune thread among several, not a bespoke gate). This generalizes §17.1's refrain-lock to the whole motif registry.

### B3. Milestone tiers + the "work-backwards / demoable-MVP-at-every-tier" guarantee  · ABSENT · MED
- **Source (ARCHITECTURE §10.1, verbatim):** *"the book is built so that at each milestone, a meaningful artifact exists and could ship if the project halted there."* A 9-row Tier 0→8 table: Tier 0 = SEED as standalone manifesto; Tier 2 = Part I ⇒ the source doc republished; Tier 4 = Parts I–VIII ⇒ "complete operational doctrine (~25K words)"; Tier 7 = ready for `export v1.0`; Tier 8 = all formats produced. *"Each tier is meaningful … The tiered structure hedges against optimization-compulsion and completion-anxiety."*
- **Ledger has:** ABSENT as a planning construct. §2.9 has the *terminal* ship-at-90% gate and the "shelve/compress/ship" scope decision, but nothing that pre-declares **intermediate shippable artifacts** so the author can stop early with a coherent deliverable. This is the structural antidote to the completion-anxiety §2.9 only names.
- **Bake-in:** ledger §2.2 (SEED discipline) or a new §2.x — at BUILD-SEED, emit a milestone-tier table into `seed.md` (each tier = what's complete + what could ship standalone). Ties the ship-at-90% ethos to a *staircase* of exit points, not a single terminal gate. Directly serves Bo's stated "Solo Enterprise Architect / demoable MVP at every tier" methodology.

### B4. The 15 numbered SYSTEM INVARIANTS as a single `run_all_invariants.py` green/red table  · WEAKER · MED
- **Source (ARCHITECTURE §8, verbatim):** a 15-row invariant table, each with an **Enforcement** column (e.g. #2 refrain-exact → `check_refrain.py`; #8 append-only → "Claude refuses to overwrite"; #10 the Tori-mirror life-clause; #12 `[BO-WRITES]` markers survive revisions; #13 every seed↔payoff; #14 Part order immutable), closing: *"`run_all_invariants.py` … runs all 15 checks and reports green/red."* The point is a SINGLE consolidated invariant runner, distinct from per-format `verify_build`.
- **Ledger has:** §10.5 names *"`run_all_invariants.py` pattern — run all asserts, report green/red"* and §14 is the FIRST-PASS DEFAULTS CHECKLIST — but the ledger's asserts are almost entirely **production-mechanical** (mirror flags, gutter, spine, ISBN). BOOK3 §8's invariant set is **content/continuity-structural** (refrain count, concept-order, compression-pair topology, `[BO-WRITES]` survival, seed↔payoff completeness, Part-order immutability). The kit has these as *separate* audits (`audit threads`, `check refrain`, `audit dependencies`) but no single consolidated content-invariant runner mirroring §8's table.
- **Bake-in:** ledger §10 / `verify_build.py` companion — define a `run_all_invariants.py` that folds the CONTENT invariants (refrain exact+count, concept-order clean, compression-pair intact, `[BO-WRITES]` present through revisions, every seed↔payoff paired, Part order unshuffled, Class-A files outline-only) into ONE green/red report, run at GATE-4 and before `export`. §14's checklist is the production half; this is the missing continuity half.

### B5. Non-linear recommended DRAFTING ORDER + PROPORTIONAL authorship, declared at seed time  · ABSENT · MED
- **Source (SEED §2.4 + §7.1, verbatim):** the parts are *written* out of reading order — *"1. Part I (lowest-risk; Disposition doc is source) 2. Part V (most ACP-corrective; key structural test) 3. Part VI (Bo's specific examples as seeds) 4. Part II …"* — lowest-drafting-risk and seed-generating units first, Class-A emotional units LAST (*"Prologue … written after Parts I-VIII so Bo knows what the Floor must set up"*). Plus §2.1: *"Bo-exclusive sections are proportionally larger in Book 3 than in Book 1"* — authorship-class MIX is a per-book design decision, not just per-unit.
- **Ledger has:** ABSENT. §CLAUDE §3 dispatches `generate {unit} N` and `next` picks "the next unit in dependency order" — i.e. the kit assumes READING order = writing order. BOOK3 says the two deliberately differ: write the units that *generate seeds and set register* first, so downstream units inherit real (not conceptual) callbacks — which is the upstream cause of the parallel-draft callback hazard the prior delta (`_delta_secondnotebook_buildlog` D3) patches at the concretization end.
- **Bake-in:** ledger §2.5/§6 (Context Pack) + `seed.md` §7 — at BUILD-SEED emit a recommended **drafting order** (seed-generating + register-anchoring + lowest-risk units first; Class-A emotional units last) distinct from the reading order, and record the intended **authorship-class distribution** as a book-level knob. `next` should follow the *drafting* order, not the reading order. Pairs with D3's concretization pass as the two ends of the out-of-order-drafting discipline.

## GROUP 2 — VOICE / CRAFT

### B6. "Alternate candidates" convention — subtitle AND refrain ship as an author-picks shortlist, with a recommendation  · ABSENT · LOW
- **Source (SEED §1.1 + §1.8, verbatim):** the seed does not hard-fix the title furniture — it lists *"Alternate subtitle candidates (Bo picks)"* (three) and *"Alternate refrain candidates (Bo picks): 'The aperture stays open.' … 'The Disposition holds.' … 'Stochastic resonance.' … Begin again at the Floor."* then **`AEGIS recommends: "The night is young."`** The machine proposes a shortlist + a default; the human picks.
- **Ledger has:** ABSENT. §2.2 fixes the refrain as a single locked line in SEED §1 and §17.1 hard-gates its wording — correct once chosen, but the ledger has no *pre-lock* stage where the seed offers candidates. For a fresh book the refrain has to come from somewhere; BOOK3 models the "propose N + recommend 1, author confirms" handoff.
- **Bake-in:** ledger §2.2 + `templates/seed.template.md` §1.8 — the BUILD-SEED step emits a **refrain candidate shortlist + a recommended default** (and optionally subtitle candidates), which the author confirms at GATE-2; only the confirmed line is then wording-locked by §17.1. Keeps the hard refrain gate but adds the missing selection ceremony.

### B7. Flash-forward is a tracked registry OBLIGATION (preview-in-N returns-in-M), not just a §7 flourish  · WEAKER · MED
- **Source (SEED §7.4 + §4.1, verbatim):** flash-forwards are *scheduled and tracked*: *"Part I previews three collapses (returns in Part IV) and 'love as epistemic treason' (returns in Part VIII). Part V previews amnesiac reverence. Part VIII previews grief's relation to climate."* And §4.1 legalizes them: concept map entries carry *"Brief forward references allowed: Prologue (felt-but-unnamed)"* / *"Brief preview: Part I."* A preview is a registry entry with a return address, immune to the forward-reference audit.
- **Ledger has:** §2.7/§7 list "flash-forwards" as one of the 9 anti-AI-tell techniques ("gesture toward later development … use liberally") — but purely as *craft advice*, with no registry obligation and, worse, in apparent tension with GATE-3's "no forward concept references." The ledger never reconciles "use flash-forwards liberally" against "no forward refs" — BOOK3 does, via the "brief-preview-allowed" registry carve-out.
- **Bake-in:** ledger §2.7 + §2.3 (contract `Must Plant`) — record each flash-forward as a `preview → returns-in {unit}` registry entry (a seed subtype), and make `audit dependencies` treat a *previewed* concept as legal before its full-introduction module while still failing an un-previewed forward *use*. Resolves the latent liberally-flash-forward vs no-forward-refs contradiction.

## GROUP 3 — THREAD-REGISTRY / CONTINUITY

### B8. "Climate vs weather" — a named, tracked continuity device for compounding shared history across long time-scales  · ABSENT · MED
- **Source (SEED §5.2 + contracts VIII/IX, verbatim):** a load-bearing distinction threaded across units — *"Climate (compound structure of shared history) vs. weather (current moment); letting the climate eat the weather is default failure"* (Part VIII) → planted as a thread → *"Climate vs. weather distinction — returns in Part IX grief (the climate persists; the weather is impossible without the co-resident)"*. It is simultaneously a **concept**, a **motif**, and a **seed→payoff pair**, and the seed carries its own return address.
- **Ledger has:** ABSENT (book-specific content, correctly). Logged because it is the cleanest specimen in the corpus of the kit's own §7 "motif echoes with variation" + seed/payoff mechanics operating on a *single named abstraction across time-scales* — the exact pattern a fresh book must reproduce for its own domain. Not a bake-in of the term; a bake-in of the PATTERN.
- **Bake-in:** ledger §7 (illusion-of-single-authorial-act) — add "a book's load-bearing abstraction can be threaded as concept + motif + seed→payoff simultaneously; track it in ALL THREE registries (dependencies + threads + compression if it re-renders), each with the same return address" as the worked pattern, citing climate/weather as the exemplar. Reinforces B1's multi-registry point with a craft face.

### B9. Compression-pair REVISION DIRECTION is fixed by authorship class (Epilogue→match-Prologue, never the reverse)  · ABSENT · MED
- **Source (ARCHITECTURE §12 recovery table + §4.3, verbatim):** on compression-pair drift — *"Revise Epilogue to match Prologue's seeded content (since Prologue is Class A and Bo-authored, revision direction is Epilogue→match-Prologue)."* The pair's *minimum-render* module (Prologue, Class A, human-locked) is the source of truth; the *maximum-render* module (Epilogue) is the one that moves. Direction is a function of authorship class, not editorial taste.
- **Ledger has:** ABSENT. §CLAUDE §3 has `check compression-pairs` (verify spiral topology holds) and GATE-4 flags orphans — but neither states **which module yields when a pair diverges**. Without the rule, a fix could "correct" the Class-A human-authored Prologue to match a Claude-drafted Epilogue — silently overwriting protected human prose, the exact Class-A violation §4/§9 forbid.
- **Bake-in:** ledger §CLAUDE §3 (`check compression-pairs`) + §10.5 asserts — record the direction rule: **on compression-pair drift, the lower-authorship-class / maximum-render module is revised toward the higher-class / minimum-render (usually Class-A) module; never edit the Class-A source to match a Class-B/C payoff.** Protects the Class-A boundary during seam repair.

### B10. Critiques/counter-doctrine RELOCATED to appendices, never appended to the doctrine body (a structural discipline)  · ABSENT · LOW
- **Source (SEED §1.2 + §2.2, verbatim):** *"Five Failure Modes critiques | Relocated to Appendix A (Robbins / Tate / Osho / Kirk / RLT); not appended to the doctrine itself."* The polemic/comparative material is quarantined in Appendices A/B so the main body holds its commitment register; the appendices carry the "here's what everyone else gets wrong" content (§7.2 cross-references them but the body never digresses into critique).
- **Ledger has:** ABSENT. The ledger has no structural rule about **where argumentative/critical material lives** relative to the thesis body. This is the structural expression of §1.4's "commitment register" (body states claims, appendix engages alternatives) — the ledger has the register rule (§17.2 "no hedging") but not the *placement* rule that enforces it.
- **Bake-in:** ledger §2.2 (SEED/structure) — for treatise/doctrine-register books, add: quarantine comparative/critical/counter-doctrine material into appendices; the body engages alternatives ONLY by cross-reference, never inline — the structural half of the commitment-register rule (§17.2/§1.4). `is_fiction:false`-adjacent.
